# Opt-in revision/overlay branches

Create a branch with `client.createScenario(ontology, {id, name, strategy: "overlay"})`. Omit `strategy` for the existing full native graph-copy design. The agent's `create_scenario` tool accepts the same explicit option. Saved overlay branches open in the existing planner branch switcher and use the same calculate, explain, review, selected-promotion and discard APIs.

Overlay creation stores only metadata: ontology, base generation/revision, version, name and timestamps. It does not project or copy the base graph, or save a JSON graph snapshot. Persisted scenario documents keep an empty compatibility `overlay` field; native delta records are authoritative. An active overlay branch is a non-expiring retention dependency at its base revision, even when no agent is currently reading it.

`BranchObject` nodes store scalar properties and one validated record per changed object, or a deletion tombstone. `BranchRelationship` markers shadow inherited relationship IDs; actual upserts are native `BRANCH_LINK` edges between scoped logical identity anchors. The shared base remains `ObjectVersion`/`HISTORICAL_LINK` visibility at the branch's generation/revision. Effective reads use Cypher to exclude shadowed base identities and union non-deleted overrides. Sorting and decoding the selected records happen in TypeScript; the application does not replay a JSON overlay to choose visibility.

An edit still loads and validates the full effective graph. Only changed records and markers are written. One Cypher query deletes/replaces touched native deltas and publishes the new scenario document/version. This avoids cross-graph candidate copying, but still assumes one API writer and does not introduce general database transactions across requests. Tests check a real runtime write error rolls the query back, a lost acknowledgment leaves the published version discoverable, same-version races reject one edit, and invalid dangling-edge edits remain invisible.

Algorithms that require a whole operational graph project the effective overlay into a temporary native graph. Explanation paths without a saved calculation read set do the same. Temporary keys are removed after success or failure and startup collection remains the orphan fallback. This projection can cost more than querying an already copied scenario. Functions/diffs/promotion also materialize effective state. Cheap branch creation is not a claim of constant-time evaluation or large-graph capacity.

Promotion retains the existing selected, property-level three-way merge and global expected-live-revision check. It is not generic first-committer-wins or serializable read-set validation. Schema changes remain additive, and the current schema validates an edit against its historical base.

Vacuum lowers its watermark to every active same-generation overlay base. Discard atomically removes native deltas and the branch document, then permits a new retention preview to advance. Branch-created logical identity anchors are not vacuumed yet. An obsolete history generation rejects reads with 409; explicit discard remains available. Ordinary logical backup exports a portable base plus derived deltas and strips storage references. Restore rematerializes those scenarios using the copy backend, so the restored branch no longer depends on a deleted history generation. Orphan delta records are collected on startup/discard/explicit scenario collection.

The two strategies are intentionally explicit while their costs are measured. A portable backup contains effective branch content, not the overlay backend choice. Do not claim historical-layer backup, zero-copy native algorithms, multiple API writers or distributed coordination.
