## What versioning means here

Each live graph mutation advances a revision. Branches now reference native FalkorDB base and working graphs, with candidate graph copies published through a versioned registry pointer. Siblings share the stored base. Before/after history remains separate. The previous JSON overlay design is supported as a migration/portable backup format. See [native graphs](native-graphs.md).

This borrows ideas from snapshot versioning and optimistic concurrency. It is **not database-native MVCC**: readers do not acquire general transaction snapshots, visibility is implemented by application-managed native revision intervals. Explicit read pins provide repeatable version-aware reads, not general write transactions or serializability. A single API process serializes coordinated mutations. Two API writers or direct database writes bypass those assumptions and are unsupported. Individual read endpoints, including multi-query traversal, are not automatically atomic across concurrent mutations.

Expected live revisions are optional on some public mutations; clients must supply them when stale-write rejection is required. Scenario edits require an expected branch version. Promotion requires branch version, live revision, selected changes, and explicit confirmation. It compares base, branch, and current live values; independent property edits survive and overlapping changed values conflict. This does not validate business invariants across every combination of independently valid changes; domain validation must cover those invariants.

The first branch at a revision projects a full base graph. In the default copy backend, every branch and edit uses `GRAPH.COPY`; this has full-copy storage and serialization costs, not persistent-tree sharing or database MVCC. Acknowledged old candidates are removed; startup/discard collection prunes unreferenced native keys. Functions, edit validation and diffs still load full graphs. Native algorithm calls query branch topology directly. Native interval visibility, historical state/traversals/calculations, and leased read snapshots are implemented. Reviewed watermark vacuum protects active snapshots and prunes bounded batches. The opt-in native overlay backend instead stores a pinned base plus native delta records. Its edits publish deltas/version in one query; algorithms project a temporary graph. Optional bounded v2 backups preserve retained history in a fresh generation; v1 remains an operational snapshot.

Tests now include simultaneous requests against the same branch (one succeeds and one receives 409), two independent branches merging separate properties, overlapping promotion conflict rejection, live-state isolation, and reading a persisted branch through a fresh store/service instance. These establish useful single-server behavior, not distributed correctness.

## Scope priorities

For the GPU application and a defensible engineering article, prioritize the items below rather than full Helix Foundry parity:

1. Configure a small real source and one real model; demonstrate source → graph evidence → isolated alternatives → reviewed action.
2. Profile actual dependency queries and measure how native traversal scales with graph size/topology and concurrent readers.
3. Remove measured platform bottlenecks: full-state mutation planning, full-state function views, globally serialized consistency work.
4. Measure branch storage, creation, edit, evaluation and promotion costs; improve only the expensive paths and retain conflict tests.
5. Add restart/failure experiments and document exactly what survived and what needed reconciliation.

Distributed deployment, enterprise governance, dozens of connectors, and a general-purpose analytics suite are separate projects. They are not prerequisites for this demonstration.

Native count/sum/avg/min/max aggregates now execute one Cypher query with the same validated filters. The [recorded study](performance-study.md) includes before/after raw trials and plans. The [concurrent-history checker](concurrency-checker.md) records guarded-write/pinned-read/branch schedules and tests its own anomaly detection. A [two-backend branch study](branch-study.md) now measures 1k/5k objects and exposes projection cost. Larger graphs, mixed workloads and the former JSON-backend comparison remain work.

Recent verified mechanisms: [durable jobs and schedules](jobs.md), [trusted domain composition and the separate library workspace](extensions.md), [indexed function-view measurements](graph-view-study.md), reviewed native graph collection and [v2 retained-history restore](temporal-backups.md). The local graceful AOF restart drill recovered a persisted pin, restored past versions and invalidated old-generation tokens. Power-loss recovery, live provider accounts and the broader backlog remain separate.
