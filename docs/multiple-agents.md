# Owned alternatives for independent agents

Every new branch records the creating principal as its owner. Edit, object patch and discard check ownership inside the scenario service's writer queue for both copy and overlay storage. Matching versions remain required for edits. Admins can override ownership; ordinary writers cannot change another principal's branch. Legacy ownerless branches belong to `local-owner` until an admin handles them. Owner values cannot be supplied in scenario-create/edit requests. Portable backups preserve ownership; restoring does not silently transfer plans to the importing user.

Configure separate named credentials with `kind: "agent"`, read/write scopes and an ontology allowlist. Credential names are identities, so use distinct names for independent agents. Agent credentials cannot carry approve/execute/admin scope, write live objects/ingestion/sources/schedules, promote, restore or collect graphs. They may read their permitted ontology, create/edit their own scenarios, calculate, explain, investigate, propose actions and manage their own investigation jobs. Enqueuing or retrying source-write jobs is also rejected. Omitting `kind` preserves the ordinary human-token contract; it does not magically identify a token as an agent.

Server-orchestrated investigations now delegate a short-lived, ontology-bound agent credential using the caller's identity, release it in `finally`, and persist that owner with the investigation. Memory summaries come from that owner's completed investigations. Durable investigations delegate as their persisted job owner. Credentials are not stored in graph records, traces, backups or the job. Existing queued intent persists after token configuration changes; cancel its job explicitly when revoking queued work.

Human promotion is separate from ownership: a principal with write+approve can review and promote selected changes from another agent's branch using the branch version and live revision. This enables visible comparison and human selection without giving either agent promotion authority. A reviewer is a configured authority, not a cryptographic proof that a person clicked. No agent approval/execution/promotion tool exists.

## Reproducible GPU demonstration

Seed the synthetic GPU fixture, configure two named `kind:agent` tokens, and provide `GRAPH_CAPACITY_AGENT_TOKEN` and `GRAPH_DRIVER_AGENT_TOKEN`. Run `node --import tsx scripts/two-agent-demo.ts`. The capacity analyst changes Meridian's lead time on a revision overlay; the driver analyst changes the regression fix duration on a native copy. Each records an investigation and calculation; their roles, owners and modes are visible in the planner/operations history. The script verifies live state is unchanged and leaves both plans for human review in the existing promotion UI.

For a fully automated permissions exercise, `--scripted-reviewer-promote` plus `GRAPH_REVIEWER_TOKEN` explicitly promotes only the capacity alternative through the same guarded SDK call. Output labels this `scripted-reviewer`, never actual human review. The integration test runs separate agent clients, rejects sibling edits/discard/live writes/source jobs/agent promotion, verifies both saved owners and lets only the separately authorized reviewer promote. This is deterministic tool orchestration unless an actual model is configured; it is not a live multi-model evaluation, distributed coordinator, branch sharing/delegation system or per-object authorization model.

[Recorded HTTP demonstration](evidence/two-agent-demo.json): both role-bound investigations completed in deterministic-tools mode against a disposable seeded FalkorDB; live state remained unchanged, and output explicitly awaits human selection. Only the integration fixture uses the scripted reviewer.
