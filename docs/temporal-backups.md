# Retained history backups

Use `client.backup(ontology, {includeHistory: true})`, `pnpm backup ONTOLOGY FILE.json --history`, or the console's **Include retained temporal versions and commits** option. This produces `graph-backup-v2`; the default v1 export remains a smaller operational snapshot that starts a new baseline on restore.

V2 captures the active generation's retained object versions, relationship intervals, commit timestamps and retention boundary under the same single-writer queue as operational state and portable branch dependencies. Expired/pruned history and earlier generations are excluded. There is no invented pre-baseline history. Snapshot leases, credentials and executable approvals remain excluded. Overlay branches export materialized base/delta data and restore through the copy backend, independent of old generation references.

Restore checks checksum, format, schema compatibility, commit ordering/timestamps, interval boundaries, uniqueness of visible identities, typed endpoint coverage across every relationship interval and equality of the historical head with operational state. Old versions need not contain properties added later as required fields; historical schema reconstruction remains unsupported. Arrays are bounded to 20k commits, 20k object versions and 50k edge versions, and full exports above 3.9 MB fail with guidance to use volume backup so they fit the HTTP restore envelope.

Operational state, imported versions/commits, documents and the new head publish in one Cypher write. A fresh generation replaces the old read context. Imported revision numbers and original timestamps stay intact; an additional restore commit advances beyond both archive and destination heads. Revision gaps are possible; querying a nonexistent revision returns 404. Old generation selectors and snapshot tokens fail rather than selecting restored data. Clients binding numeric revisions to a particular dataset must also retain its generation.

Open imported intervals remain visible at the new head and close normally on subsequent writes. Old destination versions remain inaccessible in their prior generation until reviewed vacuum. V1 archives continue to restore operational state into a new baseline, with no past revision visibility. Neither format restores historical executable code, action approvals, schema evolution, provider secrets or external writes.

Tests restore historical edits/deletes/edges and portable overlays, check stale tokens and post-restore writes, reject re-signed malformed archives, verify pruned/empty histories, and inject an invalid nested native property after valid imported writes to prove whole-query rollback. `scripts/history-demo.ts prepare|verify` adds a persisted-pin and full-history restore drill around CI's graceful API/database restart. This is separate from untested power-loss recovery and off-host backup retention policy.

Before upgrading, save both a v2 export and a protected database volume copy outside the container. Rehearse restore in an isolated single-writer instance using the same schema/code version. To roll back code, stop the writer, retain the failed-upgrade volume for diagnosis, restore the pre-upgrade volume and matching commit, then run health/history/branch checks before reconnecting clients. Do not open newly versioned archives with older code or describe a successful logical restore as a tested binary downgrade. External effects require their own reconciliation.

Observed local drill: Node 24.19.0, FalkorDB 4.18.3/Redis 8.6.2, AOF enabled with default fsync policy, graceful API then database shutdown/restart. The prepared v2 archive retained revision 0 onward; verification returned `persistedPinRecovered`, `restoredRetainedHistory` and `oldPinInvalidated` as true. This demonstrates that exact graceful sequence, not abrupt crash or power-loss durability.

Compose may recreate the API container during `up`, so the CI drill copies its prepared archive to the runner before stopping and copies it into the new container before verification. A writable container directory does not make an archive durable. Keep real backup exports outside the application container and database volume.
