# Durable work on one API writer

The server runs a persisted job queue by default. Set `GRAPH_JOBS_ENABLED=false` to pause its worker while keeping queue APIs available. Embedded/test `createApp` instances opt in with `jobsEnabled: true`. This is one API writer with database-persisted leases, not multi-writer/distributed coordination.

`client.enqueueJob(ontology, {kind: "source-sync", sourceId, maxAttempts?: 1..5})` queues a registered remote source. CSV/JSON uploads remain explicit and are not queued/scheduled. A source handler fetches the full bounded snapshot, applies normal ownership/checkpoint/expected-revision protections and never forces conflicts. Only identified transient connection/429/5xx failures retry, with exponential backoff capped at 60 seconds and the configured attempt limit. Validation, permission and conflict failures are terminal. No external write/action execution job exists.

`client.enqueueJob(ontology, {kind: "investigation", request})` queues the existing restricted SDK agent. The job captures live revision and any scenario version. A changed context fails before the investigation starts; explicit retry creates a new job with a new context. Agent limits and deterministic/model distinction remain intact. Interrupted investigations are not automatically re-executed: previously completed tools may have saved branches, calculations or proposals. Review those artifacts before retrying.

Jobs persist owner, input, version, status, attempt, next eligible time, lease token/expiry, result/error and recovery/cancellation metadata. The worker claims through the same single-writer queue, renews its lease and fences completion by the claim token. An expired source lease may retry idempotently within its attempt bound; an expired investigation lease becomes interrupted. Source checkpoints and no-op replay make acknowledged/unknown source retry safe under the documented source semantics. There is no exactly-once claim.

`client.cancelJob(ontology, id, expectedVersion)` is owner/admin-only. Queued jobs cancel immediately; running jobs receive cooperative abort. Fetches and model requests receive the signal, and source sync checks it again inside its commit plan. Already committed work is not undone. If cancellation arrives after the operation committed and returned, the completed result can win; the cancellation-request timestamp remains visible. `retryJob` accepts only matching failed/interrupted/cancelled versions and creates a new ID. It atomically consumes that retry version and records `retriedAs` / `retryOf`, so repeated requests cannot create duplicate retries from the same terminal job; retry chains must continue from the new job. The pending-job limit applies to retries too. A graceful shutdown aborts and drains active work before closing storage.

`client.setSourceSchedule(ontology, {id, sourceId, intervalSeconds, enabled?, expectedVersion?})` explicitly authorizes recurring remote snapshot applies. Intervals are 60 seconds to seven days. Updates require a matching version and owner/admin identity. At most 20 schedules and 100 pending jobs are allowed per ontology. A due occurrence and its next scheduled time are written atomically. Missed intervals coalesce, rather than replaying every missed tick; one schedule cannot overlap its own active job. Pausing a schedule does not cancel an already queued/running occurrence. Source credentials stay in server configuration and are never placed in job/schedule records.

Operations → Jobs & refresh lists state, attempts, recovery, result/error and cancellation/retry controls. It can queue remote refresh and configure/pause/resume schedules. The GPU workflow can queue its current investigation, and explains where to track it. `jobCapabilities` distinguishes an enabled server worker from an intentionally paused embedded instance.

The HTTP restore path first stops/drains the worker, then restores and resumes its configured polling. Logical exports strip leases, mark pending work interrupted and disable schedules. Restore validates job/schedule metadata and enforces those inert states even if supplied archive values were active. Re-enable schedules or retry jobs explicitly after reviewing restored context. Internal callers performing direct core restores must stop their worker first.

Tests cover durable reopen, one claim per process, transient retry/backoff/limits, cancellation and owner/version checks, lease recovery versus interrupted-agent behavior, schedule coalescing, shutdown drain, real source/investigation jobs through SDK/HTTP routes, and inert backup/restore. Durable records survive database persistence according to its configured mode. This queue does not sandbox trusted functions, support multiple API replicas, resume an individual model tool, persist request credentials, or guarantee cancellation of an already accepted API operation.
